---
title: "Logs Should Diagnose Problems Without Exposing Secrets"
date: "2026-10-11"
tags: ["Logging", "Privacy", "Observability"]
summary: "Useful logs rely on stable event fields and correlation IDs, not complete copies of visitor input. Define the minimum data needed for diagnosis, then set retention and access limits."
---

When an incident happens, a team wants logs to answer concrete questions: Did the request arrive? Where did it stop? What kind of error was returned, and how long did the issue last? The easiest idea is to write complete requests and responses to the log. But their bodies may contain personal information, access tokens or data that should not be copied indefinitely.

The goal of a log is not to reconstruct every sentence a visitor wrote. It is to describe what the system did. A structured event can record time, service and route, stage, outcome, duration, a request correlation ID and a controlled error code. Stable fields make aggregation and filtering more reliable than searching free-form text.

## Use correlation IDs instead of large bodies

Generate a random correlation ID when a request enters the system and pass it between internal services. Logs can use it to connect validation, caching, upstream calls and the response without storing the full question. During an incident, support can ask a visitor for the short ID shown by the interface and inspect related events in a restricted operations system.

A correlation ID should not encode an email, account number or other identifying information, and it must not be mistaken for an access credential. Its purpose is to connect events, not authorise access. A visitor-facing error only needs a short diagnostic ID; it should not reveal internal service names or a stack trace.

## Keep sensitive fields out of logs

Authorisation headers, cookies, API keys and passwords should be excluded outright. Question text, message content and response bodies should be omitted by default. If a particular case requires them, limit the fields, people with access and retention period, and minimise the data. A logging platform is still a data store; calling it an observability tool does not exempt it from privacy review.

Redaction should happen before data reaches the logging system, rather than relying on every developer to remember manual cleanup. Watch URL query parameters, exception objects and context added automatically by third-party SDKs; they can quietly carry tokens or personal content. Sampling is not redaction: the sampled record may still contain sensitive data.

## Set retention and access boundaries

Retention should match operational needs. Short-lived runtime logs and long-term trend metrics can follow different rules; metrics usually retain aggregates, while detailed events can be deleted sooner. Limit access to people responsible for operation and support, and keep suitable access audits.

Good logs provide clues while actively minimising unnecessary information. Writing down the operational questions first and choosing the smallest fields that answer them is usually safer than collecting everything and deciding what to remove later.
